# タスク完了時のアーカイブ確認

## 目的

Claude Codeの1セッションは1タスクを扱う運用を前提とする。依頼されたタスクが
完了したタイミングを見誤ると、完了済みのセッションがアーカイブされないまま
残ったり、逆に完了していないのに区切りをつけてしまったりする。

このSkillは、タスクを依頼された時点で「何をもって完了とするか」をあらかじめ
意識しておき、実際にその条件を満たした時点でユーザーにセッションのアーカイブ
可否を確認する、という一連の運用を徹底するためのもの。

## 発火タイミング

- タスクの依頼を受けた時点で、着手前にこのSkillを確認する。
- 依頼内容がGitHubリポジトリでの作業かどうかで、後述の完了基準が変わるため、
  依頼を受けた段階でどちらに該当するかを把握しておく。

## タスク完了の基準

### GitHubリポジトリでの作業の場合

次の両方を満たした時点で完了とする。

1. 対象のプルリクエストがマージされている
2. マージ先ブランチ(base branch)でのCIが完了している(成功・失敗を問わず、
   実行が完了していること)

- PRがマージされただけでは完了とみなさない。マージ後にマージ先ブランチで
  CIが実行される場合は、その完了まで待つ。
- 依頼が複数PRにまたがる場合は、対象PRすべてについて上記2条件を満たした時点で
  完了とする。
- PRがクローズ(マージされずに閉じられた)された場合は、それ以上進める予定が
  ないことをユーザーに確認したうえで完了として扱ってよい。

### GitHub以外の作業の場合

依頼された内容を達成し、ユーザーからの追加確認待ちの状態がなくなった時点を
完了とする。

## 完了時の手順

1. 上記の基準を満たしたことを確認する。
2. ユーザーにタスクが完了したことを報告する。
3. このセッションをアーカイブするかどうかをユーザーに確認する。
   - アーカイブ操作を実行できる手段(例: `archive_session` ツール)がある場合は、
     ユーザーが「アーカイブする」と回答してから実行する。無断で実行しない。
   - 手段がない・使えない場合は、確認だけ行い、実際の操作はユーザーに委ねる。
4. ユーザーが「アーカイブしない」「まだ続ける」等と回答した場合は、そのまま
   セッションを継続する。

## 注意

- 完了基準を満たす前にアーカイブ確認を行わない。特にGitHub作業では、PRマージ
  直後にCIが流れている途中で確認しないこと。
- アーカイブの実行そのものは取り返しがつきにくい操作(セッションが読み取り専用になり
  コンテナが解放される)なので、必ずユーザーの明示的な同意を得てから行う。
- このSkillは「完了したかどうか」と「アーカイブするかどうか」の運用を扱うもので、
  実装内容やPRの進め方そのものは `github-dev-flow` 等、他のSkillの責務に従う。
