# GitHub開発フロー(自動化範囲の事前確定)

## 目的

GitHubリポジトリでの開発依頼は、実装→PR作成→CI対応→レビュー対応→マージ、という
複数段階にまたがる。段階ごとに「ここから先は進めていいか」を都度確認していると、
依頼者にとっては細かい確認が多すぎて煩わしいし、逆に確認なしにどんどん進めると
「そこまでやってほしくなかった」という手戻りが起きる。

このSkillは、作業に着手する前に「どこまで自動で進めるか」を一度だけ確定させることで、
以降の各段階での判断に迷わないようにする。境界を先に決めておけば、依頼者は必要な
粒度でだけ関与でき、Claudeは決めた範囲の中で止まらず動ける。

## 手順

### 1. プリセットを確定する

作業に着手する前に、次の6段階のうちどこまで自動で進めてよいかを確認する。

| # | プリセット | 範囲 |
|---|---|---|
| 1 | 調査・提案のみ | 実装はせず、方針や差分案を提示するだけ |
| 2 | 実装のみ | ローカルでの実装・コミットまで。push・PR作成はしない |
| 3 | CI対応まで | push・PR作成 + CIが赤の場合の原因調査・修正・pushまで自動。レビュー対応やマージ可否は都度確認 |
| 4 | セルフレビューまで(マージなし) | `/code-review` による自分の差分の点検・修正まで自動で行う。人やCodeRabbitのレビュー対応、マージは都度確認 |
| 5 | レビュー対応まで(マージなし) | セルフレビューに加えて、選んだレビュー方式(下記)でのレビューを受け、指摘への対応まで自動で行うが、マージは実行しない。マージ可能な状態になったところで止める |
| 6 | マージまで | 5に加えて、マージの実行まで自動で対応 |

- 依頼文にすでに範囲が明示されている場合(例:「PRまでお願い」「マージまでやって」
  「実装だけ見せて」)は、それをそのまま採用してよい。
- 明示されていない場合や、表現が曖昧な場合は、作業に入る前に必ず確認して確定させる。
  「たぶんこのくらいだろう」で進めない。後から「そこまでは求めていなかった」となる
  ほうが、事前の一往復の確認より手戻りが大きい。
- 一度確定したプリセットは、そのタスクの間は再確認しない。プリセットの境界に達した
  時点(下記)で、その先は指示を仰ぐ。

### 1-1. プリセット5・6を選ぶ場合はレビュー方式もあわせて確定する

プリセット5以上(レビュー対応まで/マージまで)を選ぶ場合は、セルフレビューに加えて
「誰の・どのレビューを受けるか」も同時に確定させる。これも作業着手前に確認し、
段階を進める中で都度聞き直さない。

| 方式 | 内容 |
|---|---|
| 人のレビュー | 人間のレビュアーにレビューを依頼し、その指摘に対応する |
| CodeRabbit(制限時は待つ) | CodeRabbitのレビューを受ける。無料枠の制限に引っかかった場合は、解除されるまで待つ |
| CodeRabbit(制限時はスキップ) | CodeRabbitのレビューを受ける。ただし制限に引っかかった場合は、レビューなしで次の段階に進む |
| スキップ | 追加のレビューは求めず、セルフレビューの結果だけで次の段階に進む |

- CodeRabbitはOSS向けの無料枠を前提とする。無料枠には制約があり、例えば
  リポジトリのスター数が少ないと自動レビューがトリガーされないことがある
  (PRコメントの「🔍 Trigger review」チェックボックス等で手動トリガーできる場合は
  試す)。月間レビュー数の上限に達している場合も同様に「制限」として扱う。
- 「制限時は待つ」を選んだ場合、レビューが通るまで他のタスクを進めてもよいが、
  この段階が完了したとはみなさない(PRの監視を続ける)。
- 人のレビューとCodeRabbitのレビューを両方求められている場合は、両方の指摘に
  対応してから次の段階に進む。

### 2. 各段階での動き方

- **依頼受付**: 要件を短く要約し、プリセットの認識合わせをする。
- **作業**: 通常の実装作業。ブランチ作成・コミットメッセージなどは、その環境・
  リポジトリの既定ルール(CLAUDE.md等)に従う。
- **PR作成**: プリセット3以上で、pushしてPRを作成する。
- **CI対応**: プリセット3以上で、CIが赤になった場合は原因を特定し、修正してpushする。
- **セルフレビュー**: プリセット4以上で、PR作成後に `/code-review` を自分の差分に対して
  実行し、指摘があれば自分で修正してpushしてから次の段階に進む。
- **レビュー対応**: プリセット5以上で、確定したレビュー方式(1-1)に従って人の
  レビュー・CodeRabbitのレビューを受け、指摘があれば修正してpushする。「スキップ」を
  選んでいる場合はこの段階自体を飛ばす。
  - プリセット5・6であっても、レビュー対応段階はCI対応・セルフレビュー(プリセット
    3・4相当)が完了して初めて着手する。CIが赤のまま、または `/code-review` による
    セルフレビューが未実施・指摘未対応のままの状態で、人へのレビュー依頼や
    CodeRabbitのレビュー起動を行わない。
- **マージ**: プリセット6でのみ、CIがgreenであること・セルフレビューとレビュー対応が
  完了していることを確認した上で、GitHub上でマージを実行する。プリセット5以下では、
  マージ可能な状態になったことを報告し、実行はしない(判断は依頼者に委ねる)。

### 3. プリセットの境界を超える判断が必要になったら

プリセットで許容された範囲を超える判断が必要になったとき
(例: プリセット3でレビューコメントへの対応が必要になった、プリセット5で
設計に関わる大きな指摘が来た、CIの原因がこのタスクの変更と無関係に見える、など)は、
そこで作業を止めて状況を報告し、次にどうするか確認する。範囲を勝手に広げて進めない。

## 注意

- このSkillは「どこまでやるか」の合意形成に関するもので、実装そのものの品質基準
  (コーディング規約やレビュー観点)には立ち入らない。それらは通常の実装作業や
  `/code-review` 側の責務。
- マージの実行(プリセット6)は取り返しがつきにくい操作なので、CI・セルフレビュー・
  レビュー対応のすべてをクリアしてから行うこと。
