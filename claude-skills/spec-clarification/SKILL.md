# 仕様検討(曖昧な仕様の深掘り)

## 目的

依頼や仕様には、曖昧なまま進めると手戻りにつながる論点(目的、範囲、入出力、
制約、完了条件など)が残っていることが多い。憶測で埋めて実装に進むと、
「そういうつもりじゃなかった」という手戻りが起きやすい。

このSkillは、実装や作業に着手する前に、曖昧な論点を一つずつ確認しながら詰め、
依頼者と合意した仕様をMarkdownの仕様書としてまとめることを目的とする。
実装そのものはこのSkillの範囲外であり、仕様確定までが役割。

## 手順

### 1. 論点を洗い出す

依頼内容を読み、まだ決まっていない・曖昧な論点を洗い出す。目安となる観点は
以下の通り(すべてが毎回必要になるわけではなく、依頼内容に応じて取捨選択する)。

- **目的・背景**: 何のために必要か、誰が使うか
- **スコープ**: 対象範囲・対象外(やらないこと)
- **入力/出力**: 何を受け取り、何を返す・生成するか
- **制約条件**: 技術的制約、既存資産との整合、守るべきルール
- **成功条件・完了の定義**: 何ができれば完了とみなすか
- **優先順位**: 論点間で優先すべきものがあるか
- **想定外・エッジケース**: 例外的な状況やイレギュラーな入力への扱い
- **他への影響**: 既存の機能・スキル・ドキュメントとの関係や競合

洗い出した論点は内部的なチェックリストとして扱い、質問の順番の目安にする
(依頼者に一覧としてそのまま見せる必要はない)。

### 2. 一問ずつ対話的に深掘りする

論点をまとめて一度に問うのではなく、**一問ずつ** 確認する。

- 最も合意形成に影響が大きい・後続の論点に波及する論点から聞く
- 1つの回答を受け取ったら、その内容を踏まえて次に何を聞くべきか都度組み立てる
  (回答によって不要になった論点はスキップしてよい)
- 選択肢を示せる論点は選択肢形式で聞き、自由記述が必要な論点はそのまま聞く
- 「たぶんこうだろう」で埋めない。少しでも不明な点は必ず確認する

### 3. 質問をやめるタイミング

内部チェックリストの論点が一通り埋まったと判断できても、それだけで終了と
みなさない。**依頼者から明示的なOK**(「これで進めて」「OK」「その内容で」等)
が出るまで、疑問が残っていれば質問を続ける。

- 論点が一通り埋まったら、一度Markdownの仕様書ドラフトを提示する
- ドラフトに対して依頼者から追加の指摘・修正が来たら、それを反映して再提示する
- 明示的なOKが出た時点で仕様確定とする

### 4. 仕様書としてまとめる

確定したら、会話内にMarkdown形式で仕様書を提示する。フォーマットの目安:

```markdown
# <対象の名前>仕様

## 目的・背景

## スコープ
- 対象:
- 対象外:

## 詳細仕様
(論点ごとに決まった内容を記載)

## 制約条件

## 成功条件・完了の定義

## 保留事項
(あれば。今回は決めず、実装時や別途判断とした事項)
```

論点が少ない・軽微な依頼の場合は、この型に無理に当てはめず、決まった内容を
簡潔な箇条書きでまとめる程度でよい。

### 5. 次の工程へ引き継ぐ

仕様書が確定したら、このSkillの役割は終了。実装作業は通常の作業として進める
(GitHubリポジトリでの実装であれば `github-dev-flow` 等、他のSkillの手順に従う)。
このSkill自身が実装に着手することはない。

## 注意

- 対象トピックは問わない。コード実装に限らず、文書作成・設計・企画など
  「仕様や要件を詰める」場面であれば適用してよい。
- 依頼者にとって質問が多すぎると感じさせないよう、論点は無関係なものまで
  広げず、その依頼にとって本当に曖昧な部分に絞る。
- 仕様確定後に前提が変わった場合(方針転換など)は、変わった部分について
  改めてこのSkillの手順で確認し直す。
