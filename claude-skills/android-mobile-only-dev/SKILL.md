# スマートフォン単体 + Claude CodeでのAndroid開発

## 目的

Android Studioを開かず、PCも使わず、スマートフォン上のClaude Code(CLIアプリ/Web)
だけでAndroidアプリを開発・運用する体制には、「ローカルでビルドが完結しない」
「実機での動作確認そのものに一手間かかる」という、通常のAndroid開発とは異なる制約が
ある。このSkillは、その体制を初めて組むとき・既存プロジェクトで踏襲するときに
必要な開発フローの前提と勘所をまとめる。

## 前提: ローカルでビルドが完結しない

- 多くの開発サンドボックスにはAndroid SDKが無く、Android用Mavenリポジトリ
  (`dl.google.com`等)にも接続できない。この場合Gradleプラグインの解決すら失敗し、
  `./gradlew assembleDebug`のようなコマンドをローカルで最後まで実行することはできない。
- 着手前にこの制約の有無を確認し、無い場合は「コードを丁寧に読んで検証し、実際の
  ビルド確認はCIに任せる」という方針を明示する。`./gradlew`がローカルで最後まで
  実行できる前提を置かない。
- CLAUDE.md等のプロジェクトドキュメントに、この制約と検証方針(コマンド例・CIへの
  委譲方針)を明記しておくと、セッションが変わるたびに同じ調査をやり直さずに済む。

## 開発ループ: 依頼 → 実装 → push → CI確認 → 実機インストール

スマホ単体開発では、次のループを1つの作業単位として回す。

1. 実装し、コミット・push・PR作成する(具体的な自動化範囲・レビュー方式は
   `github-dev-flow`で確定させる)。
2. CI(例: GitHub Actions)のビルド完了を待ち、失敗すればログを確認して修正・再push
   を繰り返す。ここで初めて「実際にビルドが通るか」が判明するため、ローカルで
   構文確認した程度で「ビルドできるはず」と報告しない。
3. CIが生成したAPK(ArtifactまたはRelease)を実機にインストールし、実際にアプリを
   操作して動作確認する。UI変更・権限まわり・通知・バックグラウンド処理など、
   コードレビューだけでは検知できない不具合(実機の権限ダイアログ、通知の表示崩れ、
   端末固有の挙動等)はここで初めて見つかることが多い。
4. 問題があれば1に戻る。

## デバッグ署名鍵を固定する

- Android Gradle Pluginのデフォルトは`~/.android/debug.keystore`を使うが、CIの
  runnerは実行のたびにまっさらなVMになるため、ビルドごとに異なる鍵が自動生成
  されてしまう。署名が変わると、実機に既にインストール済みのAPKへ新しいAPKを
  重ねてインストールできず「アプリがインストールされていません」というエラーに
  なる。スマホ単体開発では毎回アンインストールしてから入れ直すのは非現実的なため、
  これは致命的な摩擦になる。
- 対策: `debug.keystore`をリポジトリにコミットし、`signingConfigs.debug`で
  明示的に指定する。中身が公開されても問題ないデバッグ専用の鍵であることを
  確認した上で行う。

## APKの配布・アプリ内アップデート(Google Playを使わない場合)

- 全ブランチのpush/PRで毎回ビルドし、作業ブランチの段階でもビルドエラーを検知
  できるようにする一方、「常に最新の安定版を指す固定URL」としてのRelease更新は
  mainブランチへのpushイベントに限定する(例:
  `if: github.event_name == 'push' && github.ref == 'refs/heads/main'`)。作業
  ブランチへのpushのたびに固定タグが未マージの内容で書き換わってしまう事態を
  避けるため。
- CIのArtifactは一定期間(例: 90日)で失効するが、GitHub Releaseは失効しない
  ため、長期の配布・アプリ内アップデートチェックにはReleaseを使う。
- Google Playを使わない場合、Play Coreのアプリ内アップデートAPIも使えず、
  `versionCode`/`versionName`も固定運用になりがちでバージョン比較に使えない。
  コミットSHA同士は「等しいか」しか分からず新旧の順序比較はできないため、CIの
  実行番号(例: `GITHUB_RUN_NUMBER`)のような単調増加する値をビルド番号として
  アプリに埋め込み、Release本文にも同じ値を埋め込んで比較する。
- これにより、アプリがGitHub Releaseの最新情報を定期的に確認し、新しいビルド番号
  を検知したら通知してダウンロード・インストールを促す、という「アプリ内
  アップデート」機能をGoogle Play無しで実現できる。これがあると、Claude Code
  のセッションが生成物をチャット添付で送る運用を避け、スマホ側から能動的に
  最新版を取得できるようになる。

## 実機確認・権限まわりの勘所

- 通知権限(API 33以降の`POST_NOTIFICATIONS`)、位置情報権限、正確なアラームの
  権限(API 31以降の`SCHEDULE_EXACT_ALARM`)、不明な提供元からのアプリの
  インストール許可(`REQUEST_INSTALL_PACKAGES`)など、実機の設定・ダイアログに
  依存する要素はコードレビューだけでは正しさを確認できない。権限が不足している
  場合にアプリ内で気づけるよう、該当機能を使う設定がある場合のみバナー等で案内し、
  設定画面へ誘導する導線を用意しておくと、スマホ単体運用でも気づいて対処しやすい。
- CIビルドが通っても実機での見た目・挙動が壊れていることはあるため、UI/機能変更を
  伴う場合は必ず実機にインストールして操作し、golden pathと主要なエッジケースを
  確認する。型チェックやテストはコードの正しさを検証するものであり、機能としての
  正しさの検証にはならない。

## 注意

- このSkillは開発フロー・配布体制に関するものであり、「どこまで自動で進めるか」の
  合意形成は`github-dev-flow`、Compose/Kotlinのプラグイン要件やRoom migration等の
  個別技術要素は`android-app-dev-foundations`が扱う。Android開発の依頼では
  これらのSkillと併用する。
